2026-02 | Fixing weird Couchbase DB C++ Client Performance Bug

We had a weird bug at work where our team's Couchbase DB (KV-DB with SQL language) client (Node JS wrapper around native C++ library) was having a high (10%) CPU spike every ~30mins or so, even when the container had no traffic. After thorough investiation debugging MemCached Binary Protocol message dumps and profiling, we determined that this load was coming from the server to the client, and was not a bug in either client library.


It was due to the load of JSON parsing many cluster_map_change_notification messages in a short period of time, typically a few hundred to thousand messages in a few seconds. Each of these messages were the full configuration topology of the DB cluster, therefore containing a decent amount of JSON that needed to be parsed. This parsing was the root cause of the CPU spikes. The configuration topology as well as the version ID did not change between messages, so the JSON parsing was not necessary. Interestingly, the C++ client checks if the version number has changed since the previous message, but this requires parsing the full JSON payload and still causes a CPU spike.


The fix was to add `?enable_clustermap_notification=false` in the Couchbase query string. This tells the client C++ library to not enable this feature when establishing a connection with the server. This was a convenient solution, as it meant we could implement this issue in JS land without patching or recompiling the C++ library.


Existing polling and retry behaviour means turning this flag off is safe, and leads to a noticeable performance gains, unlocking our PT team's workload and preventing random CPU spikes in production from affecting throughput. No issues have been found in any environment since deploying this fix. Importantly, there was no impact on rebalance and failover events. I am still unsure why this issue exists in the first place, and as Couchbase seem to have removed debug logging in the open source components of their library, I will probably never know.


2025-07 | A successful pen test

When I worked at an MSP, one of my tasks to perform yearly was a penetration test against an Australian investment portfolio management company.


The day started like any other, running nmap against the target environment to identify exposed endpoints. Eventually I had mapped out their office network, and I had the valuable targets, both the printing service and the networked security camera DVR. I was able to pop both with default credentials. Nice.


On the web app side of things, I found a simple stored XSS in a notes section of the application. Combined with the server not setting `HttpOnly` for the authetication cookies, this allowed for a social engineering attack that had the potential to leak the administrator users session cookies. I thought this exploit chain was rather severe, and the issue was patched promptly by using the correct jQuery function to write untrusted user text into the HTML, as well as setting `HttpOnly` on the cookies. I didn't have any colleagues to discuss this with, but I assume with some extra work it would be possible to do anything with the credentials supplied by the stored XSS vulnerability, including password reset and full administrator account takeover. From there, the sky is the limit.


Along with that, we ran a successful password phishing campaign using the online Defender Office 365 Attack Simulation tool. This was a decent program, which I would recommend in the future for anyone already using Entra/Azure and has the license capacity to run it. The license can be added/removed from the users once the campaign is finished. Best practice would be to follow up with regular phishing attempts, but this may not be feasible for all clients.


I'm not sure if I will run another pen test again. With that said, it was an incredibly fun, challenging, and exciting learning opportunity. I'd certainly consider this an accomplishment. However, I have to say, I think I did a much better job than I had any right to.
